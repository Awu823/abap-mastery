# Deep Dive — sap-process-finance-general-ledger (J58, day-to-day posting)

Read this file when the FS requires real functional-consulting depth on day-to-day G/L posting mechanics (document splitting, parallel ledgers, account determination, the Universal Journal, posting workflow) — not needed for a quick skill-discovery pass; `SKILL.md` covers that.

## 1. Document Splitting — Deriving Profit Center/Segment on Non-Assigned Line Items

A vendor invoice line only carries company code + vendor — no Profit Center or Segment. Yet the G/L view of that same document shows the payables line split proportionally across every Profit Center/Segment combination present on the expense lines. This is **document splitting**, not a custom derivation: **Document Splitting Characteristics** (config activity `Define Document Splitting Characteristics for General Ledger Accounting`) name which fields are split-relevant — **Profit Center** and **Segment** are mandatory by default — and for each **Business Transaction** + **Item Category** combination, splitting rules decide whether a line's assignment is inherited from other lines in the same document ("zero-balance" split) or left as-is.

Two mechanics an FS/TS commonly gets wrong:
- **Zero-Balance Clearing Account**: whenever splitting a document by a characteristic would otherwise leave it unbalanced per characteristic value (e.g. an intercompany or cross-profit-center document), the system auto-generates a clearing line item posting to a dedicated zero-balance clearing account — this account must exist and be configured in Automatic Account Determination (see §3) *before* the first cross-assignment document posts, or the posting fails outright.
- **Unspecified Posting (Business Transaction 0000)**: any document whose business transaction isn't classified for splitting purposes falls into this bucket, and no automatic split happens — a document type or posting scenario introduced by custom development (e.g. a new intercompany posting program) that isn't mapped to a real business transaction will silently skip document splitting, producing G/L-view line items with a blank Profit Center/Segment even though the classic-view document looks fine.

When derivation truly can't find a value, **Edit Constant for Nonassigned Processes** lets you set a company-code-level default/fallback Profit Center — but note customer-defined constants are *not* supported inside document splitting itself, only this one config-delivered fallback point.

**Practitioner implication:** if an FS/TS introduces a brand-new custom posting program or a new document type for cross-entity postings, always check its business transaction is splitting-relevant and its item category is covered in `Item Categories Used in Document Splitting` — otherwise the new flow will post successfully but silently break segment/profit-center reporting, which usually isn't caught until financial statements are drawn up.

## 2. Parallel Accounting via Parallel Ledgers — Leading vs. Non-Leading Ledger and Accounting Principle Assignment

Parallel accounting principles (e.g. local GAAP vs. IFRS vs. US-GAAP) are represented by **parallel ledgers**, not by parallel accounts or parallel company codes: the **leading ledger** (`0L` by default) is mandatory, always active for every company code, and uniquely determines the **currencies** and **fiscal year variant options** every non-leading ledger in the same company code must be consistent with. A **non-leading ledger** (`2L`/`3L` by convention) represents a *different* accounting principle in parallel, each ledger carrying its own valuation of the same business transaction.

**Which accounting principle sits on which ledger is a scoping decision, not a fixed SAP rule** — config activity `Assign Accounting Principles to Ledgers and Company Codes` is where it's actually made, and the corpus shows genuinely differing framings of "the standard": some SAP Help pages describe the leading ledger 0L carrying the corporate/group principle with local principle on a non-leading ledger, others describe the reverse (0L = local, 2L/3L = group/IFRS) as the predelivered default. **Do not assume either direction from memory or from a prior project — always verify the actual ledger-to-accounting-principle assignment in the target system's configuration before designing anything (reports, custom postings, account determination) that reads "the leading ledger's value" as if it were automatically the group/IFRS view.** This is also a one-way door in practice: reassigning which principle sits on which ledger after asset/transaction data exists is a major remediation exercise (see [Skill: sap-process-finance-asset-accounting] §2 on depreciation-area renumbering).

**Practitioner implication:** whenever an FS says "post this only for local GAAP" or "this value must match group reporting," resolve that to a concrete ledger (via the accounting-principle assignment actually configured in that system) before writing a single line of TS — "the leading ledger" is not a safe synonym for either "local" or "group" without checking.

## 3. Automatic Account Determination — Routing Business Transactions to G/L Accounts

Most "automatic" FI postings that an FS assumes just happen (GR/IR clearing accounts by valuation class, price-difference accounts, exchange-rate-difference accounts, the zero-balance clearing account from §1) are resolved by the **Automatic Account Determination** configuration activity — keyed by **chart of accounts** + **valuation grouping code** + **transaction key** (e.g. `BSX` stock account, `WRX` GR/IR clearing, `GBB` offsetting entry for inventory postings, `PRD`/`PRY` price differences). This is a single, centralized configuration surface across many processes (inventory, G/L, actual costing) — not a per-process hardcoded table, and not something a Z-development should duplicate.

A new material type, a new valuation class, or a new automatic posting scenario introduced by an FS almost always needs a **new or extended transaction-key entry** here rather than new ABAP logic to decide the G/L account. Note this is a different mechanism from **Revenue Account Determination** in Sales (condition-technique based, covered in [Skill: sap-process-o2c-sell-from-stock] §2) — both ultimately post into the same Universal Journal, but they are configured through entirely different paths, and an FS that conflates "how does SD decide the revenue account" with "how does MM/FI decide the GR/IR account" needs to be corrected before TS design.

**Practitioner implication:** before designing a custom BAdI/exit to "pick the right G/L account," check Automatic Account Determination first — a custom account-picking implementation is a strong signal the FS was mis-scoped as development when it is actually a configuration gap.

## 4. The Universal Journal (ACDOCA) — Single Source of Truth for FI and CO

Every business transaction that has a financial impact — O2C billing, manufacturing settlement, asset depreciation, project settlement, actual costing — posts exactly one journal entry into the **Universal Journal** (table `ACDOCA`, exposed via `I_GLACCOUNTLINEITEM`). This single table carries FI, CO (including secondary cost postings), Asset Accounting, and Material Ledger line items together, ledger by ledger — which is *why* SAP describes it as the single source of truth: there is no separate reconciliation step needed between FI and CO totals, because they were never two separate tables to reconcile in the first place.

**Do not confuse ACDOCA with `ACDOCU`** (the Consolidation Journal used by Group Reporting) — these are two distinct tables. ACDOCU is populated *from* ACDOCA via the "Release Universal Journal" task in Group Reporting, at the entity level, for consolidation purposes; a report or integration built against "the universal journal" needs to be explicit about which of the two it actually means, especially once [Skill: sap-process-finance-financial-close]'s group/local financial close processes are in scope.

**Practitioner implication:** any FS asking for a report that spans FI + CO data (e.g. "actual cost vs. revenue by cost center and G/L account") should be built as a single query against `I_GLACCOUNTLINEITEM` (or the appropriate reporting CDS cube) rather than joining separate FI and CO tables/views — the join risk (double-counting secondary postings, missing ledger-specific values) that the Universal Journal was specifically built to eliminate reappears the moment a TS re-introduces a manual join across what used to be FI-only and CO-only data.

## 5. Journal Entry Posting Workflow — Park/Hold, Verification, and Bulk Posting

A journal entry does not have to post immediately: it can be **parked** (saved, fully entered, but without G/L impact) — visible in the `Manage Journal Entries` (New Version) app together with its **workflow approval status**. Before certain journal entries actually post, the **Verify Journal Entries in General Ledger** workflow can require a defined approver step, configured per **Business Context** (e.g. company code, submitter, amount threshold) via `Manage Workflows for Journal Entry Verification - In General Ledger` and `Manage Teams and Responsibilities`. An FS requirement like "manual journal entries above a certain amount need approval before posting" is describing this standard verification workflow, not a custom approval mechanism to build in a RAP behavior pool.

For system-to-system integration volume, the correct posting path is the bulk API family already grounded in `SKILL.md` — `JournalEntryBulkChangeRequest_In` / `JournalEntryBulkClearingRequest_In` / `JournalEntryBulkLedgerCreationRequest_In` — rather than looping single-document API calls, which do not benefit from the same batching/performance characteristics and can hit rate or volume limits under load.

**Practitioner implication:** if an FS describes an approval chain for manual postings, first check whether `Manage Workflows for Journal Entry Verification` already covers the scenario (business context + team/responsibility routing) before proposing a custom workflow — and for any integration expected to post more than a handful of documents per run, confirm the bulk API is used, not a per-document loop.
