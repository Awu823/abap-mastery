# Deep Dive — sap-process-projectsystem-internal-project (1A8)

Read this file when the FS requires real functional-consulting depth on Internal Project Management (project profile choice, budget control, settlement, overhead allocation) — not needed for a quick skill-discovery pass; `SKILL.md` covers that.

## 1. Project Profile — the one field that decides everything, not the WBS shape

The WBS structure (`I_ENTERPRISEPROJECT`/`I_ENTERPRISEPROJECTELEMENT`) looks identical whether the project is customer-billable or not — what actually drives accounting behavior is a single header field, the **Project Profile**, and per SAP "there can only be one project profile per project." An FS that says "internal project, no customer billing" only rules out one of four profile types; it does **not** by itself tell you which of the remaining three applies:
- **Overhead Project** — plan/post costs, then at period-end apply overhead (costing sheet) and settle to a cost center. This is the default 1A8 pattern and the one the rest of this deep-dive assumes unless stated otherwise.
- **Investment Project** — same cost collection, but releasing the WBS element auto-creates an **Asset Under Construction (AuC)** in Asset Accounting; costs settle there instead of a cost center, then on to a completed fixed asset. "Internal, no billing" projects that exist to *build something capitalizable* (new equipment, internally constructed facility) are Investment Projects, not Overhead Projects — see §6.
- **Statistical Project** — the statistical flag applies to the whole WBS hierarchy and cannot be changed after first save; at WBS-element level you set a **default cost center** that actually absorbs the costs. Statistical WBS elements cannot be settled and cannot carry overhead — this is a much lighter "cost tracking only" pattern that some FS authors describe without realizing it's a distinct profile from Overhead Project.
- **Project with Revenue** — requires the **billing element** flag and a sales-order-item account assignment; this is the J11 (customer project) territory, not 1A8 — see [Skill: sap-process-projectsystem-customer-project].

Also worth flagging to any FS author coming from an on-premise background: **Internal Orders are not supported in SAP S/4HANA Cloud Public Edition** — "use projects instead" is SAP's own guidance. So a WBS-element-based internal project (1A8) is not one option among several for internal cost collection in Cloud, it is the mandatory replacement for what used to be an Internal Order.

**Practitioner implication:** before designing any 1A8 build, ask explicitly which of the three non-billable profiles applies — "no settlement/overhead build needed" (Statistical), "settle to cost center periodically" (Overhead), or "settle to an Asset Under Construction" (Investment) — each has a materially different Coding/Config Implementation Plan, and getting this wrong means designing the wrong settlement chain in §4/§6.

## 2. WBS Processing Status — the lifecycle gate that blocks most "why can't I post" bugs

Every project and WBS element carries a **processing status** with a fixed sequence: **Created → Partially Released (system-set only) → Released → Completed → Closed**, plus an orthogonal **Locked** state available at any point except Closed. Status changes cascade automatically both ways in the hierarchy — releasing a parent auto-releases any still-Created children; when all lower-level WBS elements reach Completed, the parent is eligible to move to Closed; child elements follow a Completed/Closed parent automatically.

The processing status is not cosmetic — it gates real transactions. Per SAP's status/operation matrix: purchase requisitions, purchase orders, goods receipt/issue, supplier invoices, expense postings, activity allocation, resource staffing, time recording, and settlement (both from the project to a receiver and from orders to the project) are all **blocked while the WBS element is in Created status** and only become possible once **Released**. They remain possible in Completed status (you can still post further costs even though the structure is frozen) but are blocked again once **Closed**.

**Practitioner implication:** "user reports they cannot post costs / create a PR against this WBS element" is very often a processing-status problem (still Created, or already Closed/Locked), not a data or authorization bug — check `ProjectElementProcessingStatus` before investigating further downstream. This also matters for [Skill: fs-logic-behavior-translator] when an FS asks for a custom "can't touch this WBS" rule — check whether standard status control already does it.

## 3. Budget Availability Control — tolerance limits are per Activity Group, not one blanket switch

Budget Availability Control (BAC) is configured as a **Budget Availability Control Profile** assigned to the project, containing **Tolerance Limits** per **Activity Group** — a bundle of business transactions that should be checked identically. The **All Activity Groups (++)** entry is mandatory (with either a warning or an error message type); other groups — Purchase Requisition (01), Purchase Order (02), HR Payroll (03), Concur Travel Expenses (04), CO Periodic Activities (05), CO Activity Allocation (06), ACE Accruals (07), Master Data Change (50), Budget Change (51) — are optional and layer a *different* threshold/severity on top of the default for that specific transaction type. Example from SAP's own docs: if `All Activity Groups` is set to warning at 100% and `Purchase Order (02)` is separately set to error at 200%, creating a PO checks *both* limits (warning at 100%, hard error at 200%), while posting a Goods Receipt or Supplier Invoice — which isn't separately configured — only checks the 100% "All Activity Groups" warning.

The budget itself is stored via **plan categories** — SAP delivers `BUDGET01` (Project Budgeting) and `BUDGET02` (Cost Center Budgeting) — which is a distinct concept from an ordinary cost plan/forecast; only BAC-relevant plan-category amounts are enforced at transaction time, loaded via SAP Analytics Cloud templates or the **Import Financial Plan Data** app.

**Practitioner implication:** "the system should block/warn when a PO exceeds project budget" in an FS is a BAC-profile + Activity-Group configuration question (which transaction type, which tolerance %, warning vs. hard error) — not custom ABAP validation logic. Also confirm with the FS author whether "budget" means the enforced `BUDGET01` category or a separate planning value that is only used for reporting — the two are not automatically the same number.

## 4. Settlement Rule generation and periodic settlement to the responsible cost center

For an **Overhead Project**, period-end processing must move accumulated costs off the WBS element to a receiver. The **Generate Settlement Rules – Projects** app (CJB1) automates this rather than requiring manual maintenance (which SAP flags as "time-consuming and runs the risk of inconsistencies, especially for complex project hierarchies"): it assigns a **Settlement Profile** to the WBS element (which determines allowed receivers) and generates **Distribution Rules** (percentage/equivalence-number splits) — the combination is the settlement rule. For overhead projects specifically, the generated rule defaults to a **periodic settlement of 100% to the WBS element's responsible cost center**. The rule can still be hand-edited afterward via **Manage Settlement Rules - Projects** (F6842).

Two escape hatches worth knowing: (1) projects with profile **Project with Revenue (YP05)** need no settlement at all — CJB1 generates nothing for them, because revenue flows directly via the billing element (again, J11 territory); (2) if a WBS element should never be settled (costs meant to stay on it permanently), assign settlement profile **YNS (No Settlement)** in the **Project Control - Enterprise Projects** app instead of running CJB1 for it.

**Practitioner implication:** don't assume "settlement rule" always means "one WBS, one receiver" — for complex multi-level hierarchies, run CJB1 periodically (typically as part of period-end close, see [Skill: sap-process-finance-financial-close]) rather than hand-maintaining every WBS element's rule; and if a specific WBS is deliberately meant not to settle, that's a settlement-profile choice (YNS), not a bug in the generation run.

## 5. Overhead cost allocation via Costing Sheet — before settlement, not instead of it

A WBS element (depending on its Project Profile) carries a **costing sheet** parameter that drives period-end overhead calculation. The **Actual Overhead Calculation (Projects and WBS Elements)** app runs this as a schedulable background job: it takes the primary cost elements already posted to the WBS as the allocation basis and calculates an overhead surcharge, posted via the CO process **Actual Overhead (Periodic)** using a secondary "overhead allocation" cost element. This calculated overhead amount then becomes part of what the settlement run (§4) moves to the cost center — the two steps are sequential, not alternatives. **Statistical WBS elements cannot carry overhead at all** (consistent with §1 — they're a lighter cost-tracking-only pattern), so if an FS expects overhead absorption on a project, the profile must not be Statistical.

**Practitioner implication:** period-end sequencing matters — run Actual Overhead Calculation *before* the settlement run, otherwise the settlement moves only the direct costs and the freshly calculated overhead surcharge is left stranded on the WBS until the next cycle. This is a close-calendar dependency, not just an app-configuration detail — cross-check with [Skill: sap-process-finance-financial-close]'s period-end closing sequence when an FS bundles project closing into a broader month-end process.

## 6. When "internal project" secretly means Investment Project — Asset Under Construction settlement

Not every non-billable project is an Overhead Project. If the WBS element's purpose is to accumulate cost that will ultimately be **capitalized as a fixed asset**, the correct profile is **Investment Project**, and the settlement chain is fundamentally different from §4: releasing the WBS element (via its assigned **Investment Profile**) auto-creates an **Asset Under Construction (AuC)** in Asset Accounting. SAP recommends this WBS-based approach over an "independent AuC" (creating the AuC directly in Asset Accounting without a controlling WBS), which is planned for deprecation.

Two settlement variants exist, chosen via the Investment Profile's event-based-settlement indicator:
- **Ordinary settlement incl. periodic settlement to AuC** — recommended for large/long-running projects: invoices accumulate on the WBS element and are cleared to the AuC periodically (via the same CJB1/Run Settlement apps as §4, just with an AuC receiver).
- **Event-based settlement** — recommended for smaller investment projects: every posting to the WBS settles to the AuC immediately, no periodic batch step, but 100% of costs are capitalized (no preliminary allocation to other receivers).

Either way, a **second, separate final settlement** step then moves the AuC to one or more manually-created **Completed Assets** (percentage, amount, or equivalence-number split per the settlement profile). For hierarchies with many WBS levels, the **Pass-Down Settlement Rule** indicator (set at project creation, "With Pass-Down Option") propagates one WBS element's settlement receiver down through all its child elements automatically, until a lower-level WBS element sets the indicator again itself — this avoids manually re-entering the same receiver on every child node. One capitalization-specific gotcha: **down payments can be settled from the investment project to the AuC, but the AuC cannot do its final settlement to a completed asset until any down-payment balance on it has been fully cleared** — relevant whenever an FS's internal/capital project involves advance supplier payments.

**Practitioner implication:** "internal project that also results in a new fixed asset" is not an Overhead Project with an extra step tacked on — it is a different Project Profile with its own settlement chain (WBS → AuC → Completed Asset), its own Asset Accounting master-data prerequisite (an asset class flagged "Asset under Construction for Investment Measures"), and its own app set (Project Control - Enterprise Projects with Investment Profile, Manage Settlement Rules, Run Settlement - Actual, Manage Fixed Assets). Flag this as a scope question back to the FS author before designing the WBS — see [Skill: sap-process-finance-asset-accounting] for the AuC-to-completed-asset capitalization posting mechanics on the receiving side.
