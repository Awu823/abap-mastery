# Deep Dive — sap-process-production-repetitive-planning (BJH, planning)

Read this file when the FS requires real functional-consulting depth on repetitive manufacturing planning (why there is no order-release step, production version/PCC setup, MRP behavior for REM materials) — not needed for a quick skill-discovery pass; `SKILL.md` covers that.

## 1. Why REM Has No Order-Release Step — the mechanism, not just the label

MRP nets requirements for a REM material with the exact same net-requirements logic as discrete/process materials (see [Skill: sap-process-production-discrete-planning] §2 for the shared MRP mechanics — not repeated here). What differs is the **receipt element**: for a REM material, MRP always creates a **Planned Order** (order type `LA` when created directly in the planning table without a BOM selection method, or `PE` when the alternative-selection indicator auto-assigns it to a production line) — and this planned order is **never converted** to a released production/process order. It IS the run schedule quantity. Reducing it (fully or partially) at backflush is the closing event for that production interval — there is no separate REL → CNF → TECO → DLV status lifecycle the way a discrete order has (that lifecycle exists on the execution side of this exact scope item — see [Skill: sap-process-manufacturing-repetitive-execution] for how the backflush reduces it).

**Practitioner implication:** if an FS uses "production order" language for what is actually a mass/flow production line, verify against the material master's Repetitive Manufacturing indicator and REM profile before assuming discrete order-release logic — REM eliminates an entire TS section (no release/goods-movement-per-order-status design needed) and replaces it with planned-order-reduction logic instead.

## 2. Production Version — Mandatory in REM, Not Just "Recommended"

In discrete planning, a production version is used mainly to resolve BOM/routing alternatives; in REM it is a hard prerequisite with a specific activation sequence: the material master must first have the **Repetitive Manufacturing indicator** selected and an **REM Profile** assigned (MRP 4 view) — only then does the **REM Allowed** indicator on the production version become meaningful ("the indicator is only applicable if you have selected the Repetitive Manufacturing indicator... and specified an REM profile"). The production version determines the BOM alternative, the routing (task list type/group/counter — rate routing is the recommended task list type for REM lines, since it schedules by line rate/cycle time rather than per-operation lead times), lot-size validity range, and the **production line** (a work center or line hierarchy). A material can have multiple production versions across different validity periods or lot-size ranges at plant level — and in REM, **each production version gets its own Product Cost Collector** (§3), unlike discrete where multiple orders for one material share the same costing regardless of version.

**Practitioner implication:** an FS that says "assign a BOM and routing to this material" for a REM line needs a Production Version row in the TS data model, not a bare BOM/routing pair — that production version is the join key to the Product Cost Collector and to the production line capacity, not a free-standing config object.

## 3. Product Cost Collector — the cost object that replaces order-based costing

The PCC has order category **05** (Product Cost Collector), delivered order type **YBMR**. Prerequisites to create one: REM indicator + REM profile on the material master, and a production version with REM Allowed selected. **Controlling level is always Production Version** in the current release — meaning you create exactly one PCC per production version, never per material alone and never per production run. A PCC has no natural end-of-lot: its validity can span an entire product lifecycle across multiple fiscal years, unlike a production order's single-lot lifespan. Its settlement rule always uses type **PER (Periodic)** — driven by default rule STR (Tracing Factor Determination) in the "Define Cost-Accounting-Relevant Default Values for Order Types and Plants" configuration activity — which is why REM always uses **Product Cost by Period**, never Product Cost by Order. A dedicated app, "Create Product Cost Collectors - Production Versions - Collective," mass-creates PCCs for every REM-enabled production version across a plant/material range in one run — relevant for a rollout/migration TS instead of manual one-by-one creation.

## 4. MRP Mechanics for Repetitive Materials — same net-requirements logic, different line assignment

Because the underlying MRP net-requirements/lot-sizing/safety-stock logic is unchanged (again, see the discrete-planning skill for that shared mechanic), the REM-specific design questions are about **production-line assignment**, not requirements calculation: (a) the **Alternative Selection Indicator** on the material master lets the MRP run itself auto-pick a production version (= production line) using configured selection logic; (b) **Quota Arrangements** proportionally split planned orders across multiple lines/production versions by percentage — an FS describing "split production 60/40 across two lines" is a quota-arrangement configuration question, not custom allocation logic; (c) with neither set, planned orders land unassigned in the Planning Table (§5) and a planner manually assigns them to a line.

## 5. The Planning Table — period/quantity buckets, not an order backlog

The Planning Table is REM's equivalent of a discrete planner's worklist, but organized by **time buckets per production line** rather than a chronological list of individual orders — planned independent requirements (from Demand Management) or sales orders (depending on planning strategy) form the basis, and planners check/revise production quantities per period view. Planners can also create AND assign planned orders manually straight in the Planning Table, bypassing MRP entirely for a quick ad-hoc plan.

**Practitioner implication:** an FS asking for a "production schedule view" on a REM line is very likely describing a Planning-Table-equivalent (period buckets by line), not a Gantt/order-list view — confirm the required bucket grain (shift/day/week) before designing a custom Fiori list report.

## 6. Make-to-Order REM — planning strategy carries over, but cost-object linkage changes

Planning strategy (MTS/MTO/hybrid — see [Skill: sap-process-production-discrete-planning] §1) still governs how demand connects to REM supply; the material master's strategy group decides whether a material runs as make-to-stock or make-to-order REM. In **make-to-order REM**, planned orders link directly to a specific sales order item, and the produced quantity is stored in **sales order stock** — it cannot be swapped between sales orders (contrast with pooled make-to-stock REM inventory). SAP recommends a **valuated** sales order stock (goods movements post to FI immediately); a non-valuated variant exists but defers all FI postings until results analysis/settlement. Even here, the PCC is created for the **individual-requirements material** (e.g. the configurable/variant material) and costs are still analyzed **period-based across all sales orders sharing that PCC** — SAP's own automotive-line example explicitly states that per-vehicle costing is de-emphasized in favor of period-aggregate costing on the shared PCC.

**Practitioner implication:** if an FS demands "cost per individual unit/sales order" reporting from an MTO REM line, push back — standard PCC-based REM costing gives period-aggregate cost, not per-sales-order cost; that requirement needs either a custom reporting layer or a design change toward discrete/order-based costing, not a "just query it" assumption. Also do not assume [Skill: sap-process-o2c-sell-from-stock]'s standard O2C flow applies unmodified here — MTO REM production is sales-order-triggered but is not "sell from stock."
