# Deep Dive — sap-process-manufacturing-repetitive-execution (BJH, execution)

Read this file when the FS requires real functional-consulting depth on repetitive manufacturing execution (what "lean" confirmation actually decouples, reporting-point mechanics, and period-based vs event-based cost posting) — not needed for a quick skill-discovery pass; `SKILL.md` covers that.

## 1. What "Lean" Actually Means — decoupling, not skipping

REM confirmation (transaction/app "Confirm Repetitive Manufacturing," MFBF) can post goods receipt of the finished product, goods issue for components (backflush), and production-cost/activity posting all in ONE coupled transaction — or **decouple** them in time: post the goods receipt immediately for throughput, and let backflush/activity posting catch up later during quiet production periods, explicitly to cut system response times when entering high volumes of confirmation data. It also supports **Collective Entry of Confirmations** (MF42N) — confirming actual data for ALL materials produced on a given production line in one pass, rather than material-by-material. This is structurally different from discrete/process order confirmation (CO11N/CO15-style), which is inherently per-order.

**Practitioner implication:** if an FS insists "confirmation must post everything in one shot, no exceptions," check whether that is a genuine business rule or just a description of the coupled default — REM's decoupling is a performance/workload feature, not something that needs disabling to satisfy a compliance requirement.

## 2. Backflushing — components determined at confirmation time, from one of 3 possible BOM sources

Backflushing means the system posts the component goods issue automatically at the moment of a goods-receipt or reporting-point confirmation, instead of the operator manually issuing each component. At that moment, the system explodes **one** of: the **current BOM**, the **revision-level BOM** (if BOM revision-level tracking is used), or the **planned order's own BOM** (frozen at planning time) — which source applies is a config/master-data decision, not incidental, and it matters because an engineering change to the BOM between planning and confirmation date changes which components get backflushed depending on this setting.

**Practitioner implication:** a "wrong component consumed" defect on a REM line is very often a BOM-source-setting mismatch (current vs. planned-order-frozen), not corrupted master data — check this setting before assuming a data problem.

## 3. Reporting Points — the only real mid-line checkpoint REM has

Reporting points are operations flagged in the routing with a control key carrying indicator **"1 = Milestone Confirmation."** The REM profile decides whether reporting points are used at all, and if so whether confirmation there is **mandatory** (post at every reporting point; maximum control, maximum effort, one document per reporting point) or **optional** (normally confirm only at the end of the line, but able to post scrap or a WIP snapshot at a reporting point when needed). At a reporting-point confirmation: all components consumed **between the previous reporting point and this one** are backflushed, the activities for that operation are posted, and dependent requirements of the **oldest outstanding run schedule quantity** are reduced (a FIFO-like consumption — not necessarily "this run's own" requirement, a common FS misconception). Scrap can be posted directly at a reporting point either for the **assembly** (posts activities + component goods issue) or for a **component alone** (posts only that component's goods issue) — these map to distinct confirmation processing types with different downstream postings (§4).

A missed reporting point can be caught up via "Backflushing Reporting Points Subsequently" — e.g. confirming reporting point 10 for an accumulated 200 pieces after the fact. The REM profile can also auto-trigger the finished-assembly goods receipt the instant the **last** reporting point is confirmed, sparing the operator a separate final GR step — mainly useful in mandatory reporting-point setups.

**Practitioner implication:** for any FS describing a multi-stage repetitive line with "semi-finished visibility mid-line" or "WIP value at week-end," reporting points ARE the mechanism — don't design a custom intermediate-goods-receipt step; map it to a control-key + REM-profile (mandatory vs. optional) configuration decision instead.

## 4. Confirmation Processing Types — how "goods receipt without an order" actually works

The Repetitive Manufacturing Confirmation business object's `RptvMfgConfProcessingType` field is the literal technical proof of "backflush against a Product Cost Collector, not an order." Types split by scenario: **Assembly Confirmation (B)**/**Assembly Scrap (BS)** apply to both MTS and MTO and represent the finished-product goods receipt; **Assembly/Activity/Component Confirmation at Reporting Point (Z/W/X)** and their scrap variants (**ZS/WS/Y**) are **MTS-only**; **Assembly Scrap up to Reporting Point (ZB)** and **Excess Component Consumption at Reporting Point (ZZ)** are MTS-only correction types; **Activity/Component Confirmation after Last Reporting Point (I/J)** and their scrap variants close out a mandatory reporting-point sequence. Critically, `ConfHasRefToPlannedOrder` is a boolean on the confirmation object itself: a REM confirmation **may optionally reference a Planned Order** (for MRP-quantity-reduction traceability), but it **never references a released production/process order**, because none exists in REM. This is the API-level confirmation of the "no order-by-order tracking" behavior described at the process level.

Two other fields worth flagging for FS/TS mapping: `ProductionLot` — an external ID letting a REM confirmation tie to a WBS element for project-linked repetitive production (relevant if an FS combines REM with Project System — see [Skill: sap-process-projectsystem-internal-project]); and `RepetitiveMfgPlanningGroup` — groups all materials produced on one production line for planning purposes, distinct from the production version itself.

## 5. Period-Based vs Event-Based Production Cost Posting — and a deprecation deadline already in the past

Two posting modes exist for the Product Cost Collector. **Period-Based** (scope item **BEI**) calculates WIP, variance, and settlement in a batch run at period-end (calculate WIP → calculate variance → settle) — supports only the leading ledger, one fiscal-year variant, and two currencies (controlling-area and company-code currency). **Event-Based Production Cost Posting** (scope item **3F0**) posts WIP, overhead, and variance to the PCC **in real time with each business transaction** (goods issue, activity confirmation, goods receipt) — it supports parallel ledgers, multiple currencies, and group view for Parallel Accounting, and target cost is calculated **on the fly at each goods receipt**, not persisted in a batch table the way BEI's variance-calculation run (KKS5-equivalent) is.

**BEI is deprecated starting release 2408, with SAP's stated cutover deadline "by the end of year 2025."** Given that deadline has already passed as of this workspace's current date, any new REM implementation should default to 3F0 unless there is a specific, already-documented reason a client is still on BEI — an FS assuming classic period-end batch settlement (KKAO/KKS5/KO88-equivalent jobs) for a **new** REM build is very likely describing a deprecated flow, and this should be flagged back to the user rather than implemented as specified.

Within 3F0 there are two sub-approaches, chosen via the event-based processing key on the PCC (`PCCEB` vs `PCCMS`), not a code-level decision: the **primary approach** posts WIP/variance fully automatically per transaction; the **Manual Settlement alternative** stays event-based/parallel-ledger-capable but keeps settlement as a deliberate batch step — used when backflush volume is very high or logistics operations don't always follow the expected sequence, to avoid an excessive number of settlement documents.

**Practitioner implication:** "how does the finished-goods cost reach Finance" for a REM line is a period-based-vs-event-based configuration answer, not custom FI posting logic — see [Skill: sap-process-finance-financial-close] for how PCC period-end jobs fit the closing calendar, and [Skill: sap-process-finance-general-ledger] for where the resulting WIP/variance journal entries land in ACDOCA.

## 6. Embedded EWM Interaction — a hidden hard constraint on backflush posting mode

If components are managed by an embedded Warehouse Management system, REM confirmation carries one structural restriction discrete execution doesn't have: only the **finished product** may sit in an EWM-managed storage location for the confirmation itself; the **production storage location** (where components are staged) must be MM-IM-managed, because the system posts the component goods issue **synchronously** at confirmation time. Unlike discrete manufacturing, **REM does not support asynchronous backflush postings** to an embedded-EWM bin (discrete can post asynchronously, e.g. via a later delivery). Practically: the REM profile's "Post synchronously to bin" indicator must be selected whenever EWM is in play for a REM line — leaving it deselected is not a valid alternative configuration for REM the way it can be elsewhere.

**Practitioner implication:** an FS combining REM with embedded EWM warehouse operations (see [Skill: sap-process-supplychain-warehouse-mgmt]) needs this synchronous-posting flag called out explicitly as a mandatory setting, not an optional performance tuning choice — getting it wrong causes backflush postings to fail or double-post.
